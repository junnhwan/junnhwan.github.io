01 / A MINIMUM MAP

有人提交了代码，
谁来帮他检查改动？

01

PR-Agent 是开源的 AI 代码审查工具。它从 Git 平台读取提交的改动，准备给语言模型看的材料，再把审查意见、改进建议或问题答案交回给用户。

前置：会写一点代码即可这一章先不读复杂函数目标：能用 30 秒解释项目

先理解 PR 和 Diff

Pull Request（PR）是“请把我这批改动合进目标分支”的协作请求。审查者看到改动后，可以评论、要求修改，最后再决定是否合并。GitLab 的类似对象通常叫 Merge Request。

Diff就是两个版本的差异。下面是一段教学例子：删除行以 - 开头，新增行以 + 开头。Diff 里的前缀不是 Python 语法。

@@ -1,2 +1,4 @@
 def divide(a, b):
-    return a / b
+    if b == 0:
+        raise ValueError("b must not be zero")
+    return a / b

以 @@ 开头的标题标明这个hunk（差异片段）在旧、新文件中的行位置。一个文件可以有多个 hunk。周围没改的几行有助于理解修改所在的函数。

人类审查者看什么？

修改有没有漏掉特殊输入？会不会破坏原来的行为？测试覆盖了哪些边界？

模型需要得到什么？

任务说明、PR 元信息、相关 Diff，以及当前问题等材料。输入准备代码负责把这些材料组织成 Prompt。

四个入口，对应四类用途

入口用户的意图大致输出 / 本册关联
/review“帮我审查这个 PR。”审查结果；#3291 改善大型 Diff 的准备过程。
/improve“给出具体代码改进建议。”建议列表；#2829 / #3324 处理分块失败。
/ask_line“解释我选中的这段代码。”行级问题答案；#2862 处理历史和输入预算。
A2A 接口“通过协议客户端发任务，再接着问。”任务状态与结果；#3643 恢复后续任务的 PR / Diff。

/ask_line通常由选中代码后的评论路径提供相关位置参数；此表说明用途，不保证在任何普通评论里直接输入命令就能运行。接口和配置以所读版本为准。

你看过的 Agent 概念，哪些在这里适用？

这里确实需要连接模型、工具和外部环境。但本册涉及的主要路径是命令驱动的 LLM 工作流：代码先根据命令选定工具，再准备输入、调用模型、处理输出。不能仅凭项目名里的“Agent”，就认为这几项 PR 实现了 ReAct、自主规划循环或多 Agent 协作。

LLM
生成和理解文本的模型。它依据当前传入的输入工作，不会天然知道你上一轮谈的是哪个 PR。
Git provider
访问 GitHub、GitLab 等平台的适配层。负责取 PR / Diff，或发布评论。它不是模型供应商。
LiteLLM
项目用于接入不同模型服务的库。请求仍受各模型的上下文限制、配置和错误行为影响。
Prompt
实际发给模型的任务说明与上下文。包含模板文字和插入进去的数据。
模型给出建议，不等于建议已经正确这些贡献改善的是运行工程：输入能否装下、失败结果能否保留、准备是否重复、上下文能否接续。它们没有证明模型的审查准确率提高了多少。
停下来，用自己的话回答

“PR-Agent 拿到一批代码改动后，会按命令组织材料交给模型，再输出审查或问答结果。我的这几项贡献主要完善模型调用周围的工程环节。”

能说清这句话，就有继续学习的基础。先不要背函数名。

Prompt 不是“问题那一句话”

例如用户问“这个条件为什么放在这里”，最终请求还会带上说明文字、PR 标题、代码片段、可用的历史等。项目用 Jinja2 模板把变量填进去，再交给模型。

# 教学示意：模板和最终文本的区别，不是原仓库摘录
模板：请解释 {{ file_name }} 的这段改动：{{ diff }}
变量：file_name = "math.py"，diff = 相关代码片段
渲染：请解释 math.py 的这段改动：……真实代码……

渲染（render）就是把模板占位符替换为真实数据。模板本身很短，填入 Diff 和历史后可能很长。这解释了为什么 #2862 必须对最终渲染文本计数。

项目把请求组织成 system / user 两类消息：system 放任务要求与回答规则；user 放这次的材料与问题。两部分都占输入空间。这里的 user 消息可以由程序组装，不只是你手动输入的一句话。

03 / CONTEXT BUDGET · #2862

问题只有一句，
为什么模型会说“装不下”？

03

用户围绕一段代码接着问，历史评论越积越多。当前问题很短，最终 Prompt 却可能超出模型的上下文窗口。#2862 处理的是 /ask_line 这条路径的输入预算。

前置：Prompt / 模板渲染输入预算 = 模型窗口 − 输出预留核心函数：_fit_conversation_history

先认识 Token、窗口和输出预留

Token是模型处理文本的片段单位，不等于字符、单词或汉字。不同模型的切分方式可能不同；同样一段文本，计数结果也可能不同。

上下文窗口可以先理解成一次模型调用可容纳的容量。这里的代码从项目给当前模型配置的容量中，扣除输出预留，得到允许使用的输入预算。不能把整个窗口都塞满输入，再期待模型有空间写答案。

模板说明 + 代码片段 + 当前问题 + 历史
≤ 模型容量 − 输出预留

“最终 Prompt”意味着填入了真实 hunk、问题和历史的 system / user 文本。只数 Diff 或只数历史，都可能遗漏模板和其他变量。

旧问题 → 修复后的处理顺序

容易出错的想法

“之前准备时数过 Token，后来加一点历史应该没事。”或者“主模型装得下，备用模型肯定也装得下。”

这些假设会在历史增长、模板展开或模型切换后失效。

合并代码的做法

每次尝试模型调用，先把 hunk / 问题填好，再按本次实际模型计算最终 Prompt。若超限，逐步减少历史；若去掉全部历史仍超限，调用前报错。

具体到旧代码：对象初始化时历史和 hunk 还为空，TokenHandler 先计过数；运行时才加载这两部分。初始化得到的数字因此不能代表最终模型请求。

为什么保留当前问题和代码，优先裁剪历史？

模型这次要解释的就是当前问题和代码。如果先把它们删掉，请求虽然变短，回答的对象却可能变了。代码把历史作为可收缩部分，从历史文本末尾保留较新的内容，并加上裁剪标记。

它用二分搜索查找可保留的字符数：试一半；能装下就多留，装不下就少留；每次都重新渲染并计数。这样比一字符一字符地尝试更节省计数次数。

EXPERIMENT 01 / 教学预算模型

自己把历史“装进窗口”

这里把模板、代码、问题合成固定输入，并把历史切成等量教学单位。数值用于说明预算；没有接入真实 tokenizer，也没有模拟真实字符后缀的每个细节。

固定输入留下的历史（含教学标记）输出预留

预设反例：窗口 1000、输出 200、固定输入 450、历史 700。输入预算只有 800，需要裁剪历史。若固定输入本身超过 800，裁剪历史也无济于事。

现在读真实代码：先看三道判断

原源码摘录，来自 #2862 的合并提交；render_with_history 和 count_prompts 是上文定义的内部函数。

if count_prompts(render_with_history(conversation_history)) <= max_tokens:
    return conversation_history

if count_prompts(render_with_history("")) > max_tokens:
    raise ValueError(
        f"The /ask_line prompt exceeds the token limit for {model} even without conversation history"
    )

第一道：原历史就能装下，直接保留。第二道：空历史也装不下，说明不能靠历史裁剪解决。第三道在后面的二分循环里：测试候选历史，直到找到预算内的字符后缀。

再深一层：计数和裁剪有哪些限制？

优先用 LiteLLM 的 token_counter(model=..., messages=...)；失败时用该模型对应的 TokenEncoder，非 GPT 路径可能采用本地估算。不能承诺与每家模型服务的真实计数完全一致。

二分搜索的是历史字符串的字符后缀长度，不是对话轮数，不保证保留完整消息，也不是摘要算法。裁剪标记同样占空间。项目的模型容量配置若不准确，仍可能影响判断。

一个真实测试，先看它在证明什么

test_ask_line_keeps_final_prompt_within_budget_after_loading_history构造 200 条历史回复，在模拟模型窗口 700、输出预留 100 下检查最终输入不超过 600，同时确认问题、hunk 和最近的 reply 199仍在。Git provider 和模型调用使用假实现，预算使用 LiteLLM token_counter 做本地计数，没有调用真实模型。

另一个测试 test_ask_line_uses_attempted_model_for_non_gpt_prompt_budget核对调用计数器时使用尝试中的模型 claude-2；它没有真实调用 Claude。代码有“空历史仍超限”的报错分支，这个新增测试文件没有单独覆盖它，后续可以亲手补一条练习。

学完应能讲清为什么数最终 Prompt；为什么换模型要重算；为什么预留输出；为什么问题和代码本身过长时要明确报错。

04 / PARTIAL FAILURE · #2829 + #3324

四块代码，三块成功，
结果应该全部作废吗？

04

大 Diff 需要分块，分别向模型请求建议。其中一块失败时，成功块已经产生了有用结果。两项 PR 先保住这些结果，再尝试只恢复失败的块。

前置：02 / 03先学 asyncio，再看 fallback成功保留 → 定向恢复 → 顺序汇总

先补三个 Python 概念

async / await
等待网络响应时，让其他任务有机会执行。await表示等待异步操作完成；不是保证创建一个新线程。
gather
asyncio.gather把一批异步操作一起等待。结果槽位按传入顺序排列，不能按完成先后拼接结果。
fallback
当前模型尝试失败后，使用已配置的备用模型 / deployment。它可能有不同容量、速度和服务行为，不是简单再发一次完全一样的请求。

如果没有处理好异常，一块失败可能使外层直接转去整批 fallback，成功的结果不能保留下来。return_exceptions=True让普通异常以结果对象的形式返回，程序才有机会识别哪个槽位失败。

两次贡献，接上同一个故事

#2829

先保住局部成功

串行和并行路径隔离普通分块异常，留下成功结果。如果部分成功，仍能汇总出建议；不会因为一块失败就抹掉其余块。

#3324

再恢复失败槽位

在配置了可用备用模型的情况下，等待本批任务收齐，再为失败索引逐级尝试后续模型。成功索引不会重复调用。

EXPERIMENT 02 / 教学批次模拟

A、B、C、D 四个槽位

每个字母代表一块输入。这里简化为一次分块预测尝试；真实路径还可能包含建议的二次评估。本演示不调用模型，不模拟计费和调度时间。

局部失败反例：A、C、D 成功，B 失败。有可用备用模型时只恢复 B；没有或恢复失败时保留其余结果。全失败交给原有整批 fallback。取消需要向上传播。

真实代码：把“失败”留在结果槽位里

#3324 合并代码的并行分支及取消检查；省略了中间串行分支，以 …标注。

results = await asyncio.gather(
    *[self._get_prediction(model, numbered, unnumbered) for numbered, unnumbered in chunk_pairs],
    return_exceptions=True,
)
# … 这里省略串行分支 …
for result in results:
    if isinstance(result, BaseException) and not isinstance(result, Exception):
        raise result

Exception是普通错误这一类，程序可以记下来后尝试恢复。asyncio.CancelledError属于 BaseException而非普通 Exception：请求要停止时，不能把它当作“某块失败，继续重试”。

为什么等整批结束，才切备用模型？

这些调用共享本次请求的模型相关配置。若 A、C、D 还在执行，就把 deployment 改成 B 的备用设置，可能干扰同批其他操作。实现先收齐本批结果，再定向恢复，并在 finally中还原 deployment。

有效模型链放在 ContextVar里。可以先把它理解成“跟随当前异步调用上下文的槽位”，避免把一个请求的有效 fallback 链误用于并发的另一个请求。它不是跨进程存储，也不是天然让所有对象都线程安全。

为什么备用模型装不下时，不继续裁剪这一块？

恢复逻辑用备用模型的 TokenHandler 对完整渲染 Prompt 计数并预留输出。如果超过预算，就跳过这次恢复尝试。这里不把 Diff 再截短，以免成功结果和被缩短输入的结果混在一起，改变分析覆盖范围。

本路径的预算计数用 TokenHandler 分别数 system / user；与 03 章 /ask_line 优先使用 LiteLLM 消息计数的实现细节有区别。

局部失败、全部失败、取消：三种不同结局局部失败可以保留和恢复；全部失败仍交给原有整批 fallback；取消向上传播。它是当前请求内的恢复机制，不是进程崩溃后可恢复的持久化 checkpoint，也不保证每次都能取得完整覆盖。

测试怎么证明“没有重复成功块”？

真实恢复测试用 a、b、c 三块，把模型调用替换成可记录的假实现，让 b 第一次抛出普通异常。之后检查调用记录：主模型访问三块，备用模型只访问失败的 b；最后的建议仍按原始块顺序汇总。上面 A、B、C、D 四块是教学扩展示例，不代表默认分块数量。

另有回归检查等待同批结束后才切配置、较小模型预算跳过、取消传播与 deployment 还原、并发调用的有效链隔离。读这些测试时，关注访问了哪些输入、调用了几次、状态是否复原，不要只看有没有返回结果。

“准备一次”包含哪些工作？

读到 Diff 后，需要按语言整理文件、扩展差异上下文、添加行号、计算各部分 Token、再按容量把材料打成块。打包（pack）可以先理解为“把文件片段分配进若干模型输入”。

旧路径的重复

普通准备先做一批处理和计数。大型 PR 转入分块路径后，又从输入材料开始准备，重复其中一部分工作。

通过 PreparedPRDiff携带已准备材料和计数结果。后续分块用共用 packer 继续打包，同时保留文件排序和剩余文件的语义。

复用之前，必须证明输入条件相容

切换模型可能改变 Token 容量和计数。换 Token handler 实例，可能代表另一套 Prompt 变量或计数状态。行号格式变化，也会改变模型看到的文本。代码因此限定当前请求内的复用。

31.8% 应该怎样理解？

是不是已经消除了所有重复计数和网络请求？

怎样验证“更快但没有换掉结果”？

前置：PR / Diff / 一次模型调用当前显式输入优先按输入顺序找历史

A2A 先理解到这里就够了

A2A（Agent2Agent）提供客户端与 Agent 服务交换消息、发起和查询任务等接口。本项目的 mosaico把协议请求接到已有代码审查 / 问答路径。这项 PR 解决多轮上下文，不代表它实现了多个 Agent 自动分工协作。

标识 / 对象直观解释为什么需要区分
taskId某一次任务的编号每轮可以产生一个新任务。
contextId把多轮任务放在同一上下文的编号不同任务可以属于同一组对话。
owner / 用户范围服务解析出的调用者范围不能仅凭相同 contextId 读取另一个用户的历史。
TaskStore存任务状态和历史消息的地方这个实现里是进程内存，handler 与 executor 共用它。

若按完成顺序找历史，旧任务会把目标“倒带”

t1 · 输入先到Task A：审查 Diff A。A 执行慢，还没结束。
t2 · 新输入到达Task B：改审查 Diff B。B 先完成，最新输入是 B。
t3 · 旧任务完成Task A 现在完成。若按完成顺序找“最新”，会错选 A。

用户之后说“解释一下”，应该继续针对 Diff B。输入顺序反映用户最近指定的目标，完成顺序只反映运行快慢。代码在任务开始时登记输入顺序，倒序查找最近的可路由用户输入。

EXPERIMENT 04 / 教学历史路由

哪份 Diff 会被选中？

历史约定：owner U1、context C1 先输入 A，再输入 B。演示镜像路由优先级；没有运行 A2A 服务或真实 TaskStore。

同 owner / context 时，最新输入 B 优先于晚完成的 A；B 尚未完成也可以恢复其已登记输入。当前显式 C 覆盖历史。另 owner / context 不继承 U1 / C1 的 A、B。

把修复拆成五步

  1. 服务创建同一个 InMemoryTaskStore，供请求 handler 和 executor 使用。
  2. 开始处理任务时，登记 (owner, contextId)下的 taskId，并保存 working Task 的用户输入。
  3. 当前消息已有 PR / Diff，直接使用当前消息；无需查历史。
  4. 否则按输入顺序倒查以前任务，只读 user 消息，找到最近 PR / Diff 后停止。
  5. 历史和当前消息以显式消息边界交给 dispatcher；从当前往前选择上下文，保持当前输入优先。

    return []

这是“找回审查对象”，还不是无限记忆

历史查询默认最多考虑 100 个以前的任务，可配置范围 1–1000。这是任务数量上限，不是 Token 或消息数量上限。找到了最近可路由输入就停止，不需要把所有过去的 PR 都送进本次调用。

TaskStore 和输入索引都在进程内，服务重启或请求落到其他副本时，这份历史可能不可用。owner 隔离依赖服务的调用者范围解析；这项 PR 不是完整认证系统或跨进程持久记忆。

为什么不能把用户文字中的 “assistant:” 当成角色？

A2A 已经给出了消息边界。用户可能在 Diff、日志或问题中写 assistant:等字样。dispatcher 把每条历史输入明确作为 user 消息，不再把这些内容重新拆成角色，避免把代码文本误当成对话结构。

真实测试做到了哪一层？

四个贡献，逐条练习

上下文预算：为什么要在最后重新计数？

“行级问答加载历史和代码之后，最终 Prompt 可能比早期估计长。实现按实际尝试模型计数，扣掉输出预留，再二分裁剪历史后缀；当前问题和 hunk 保留。换备用模型时也重新预算。测试同时检查长度上限和关键内容保留。若不带历史仍超限，就在模型调用前报错。”

追问：裁剪单位是字符后缀，不是完整轮次；计数存在本地估算路径，所以不能承诺所有供应商都精确一致。

分块恢复：为什么不直接重跑全部块？

“一批分块里只有部分失败时，成功块已经有结果。第一项修复把普通失败留在结果槽位，第二项修复只用备用模型恢复失败索引，按原顺序汇总。先等待本批结束，避免切模型配置干扰尚未完成的调用。备用模型装不下该块就跳过，取消则向上传播。全失败仍用原来的整批 fallback。”

追问：恢复可能增加延迟和费用；不是持久 checkpoint，也没有保证最终覆盖所有块。

准备性能：31.8% 的分母是什么？

“review 处理大型 Diff 时，分块准备存在重复处理和计数。改动在请求内复用 PreparedPRDiff，并限定同模型、同 handler 实例以及带行号的相同格式；备用模型重新准备。固定离线基准里准备耗时 p50 从 59.169 ms 到 40.365 ms，约降低 31.8%。这只测准备阶段，不包括 LLM 推理。”

追问：现有记录的基准是 mock provider、50 文件 × 38 行、8 分块、20 次测量；你本人尚未亲手重跑。读过记录后再用自己的语言解释实验条件。Token 计数调用减少不等于模型 Token 费用减少。

A2A：为什么不能按最近完成的任务找上下文？

“多个任务可能完成顺序与输入顺序不同。旧任务晚完成，不代表用户重新选择了旧 Diff。实现按同 owner / contextId 的任务输入索引倒查，只找用户消息中的最近 PR / Diff，当前显式输入优先，并限制历史任务数量。服务和 executor 共用 TaskStore，working 任务的输入也可被接续。”

追问：历史在进程内；重启或跨副本可能丢失。这个功能恢复审查对象，不是完整长期记忆系统或认证系统。

术语速查

PR / Pull Request把分支改动申请合并到目标分支的协作请求。不是 Prompt。
Diff / patch / hunk版本差异 / 文件改动文本 / 文件内的一段差异片段。
Prompt / render发给模型的任务与材料；render 是把真实数据填入模板。
Token / tokenizer模型处理文本的单位 / 切分计数工具。不同模型可有不同计数规则。
Context window一次调用的容量。本文输入预算还需要扣除输出预留。
Output reserve给模型生成结果预留的空间；不是历史长度。
Git provider访问 GitHub、GitLab 等平台的适配器。
LiteLLM / handler模型服务的调用库 / 项目的适配类。不能自动消除模型差异。
asyncio / gatherPython 异步执行支持 / 等待一批操作并按输入顺序返回槽位。
Exception / cancel普通失败可记录或恢复；取消代表停止请求，需要向上传播。
Fallback / deployment备用模型链 / 对应服务部署配置。恢复前要检查预算，结束后还原配置。
ContextVar跟随当前调用上下文的变量槽位，用于隔离并发请求的有效模型链。
PreparedPRDiff / pack准备好的 Diff 数据容器 / 把材料分配为多个输入块的过程。
p50 / benchmark测量结果的中位位置 / 在明确条件下做的性能实验。
A2A / TaskStoreAgent 消息与任务协议 / 存放任务状态和历史的对象。
owner / contextId调用者范围 / 多轮任务的上下文编号；共同限定历史查找范围。
taskId / working某次任务的编号 / 任务执行中的状态。执行中的输入也可接续。
mock / stub / assert测试中替换外部依赖的模拟 / 简化实现 / 必须成立的断言。
