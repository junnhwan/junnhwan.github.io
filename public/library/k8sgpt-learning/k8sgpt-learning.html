spec 是目标，status 是观察到的现状

教学用片段 · 不是完整的可部署 YAML
metadata:
  name: orders
  generation: 8       # 对象目标的版本标记
spec:
  replicas: 3         # 我希望有 3 份
status:
  observedGeneration: 7
  readyReplicas: 2    # 状态记录了 2 份就绪

这里有两个不同的问题

数量：希望 3 份，当前记录的就绪数量是 2。

时效：目标已经到第 8 版，控制器状态仍只观察到第 7 版。这个状态可能还没反映新目标。

保存配置成功，不意味着应用立即到位。API 对象的更新、控制器的处理、容器启动和状态回写是异步过程。

“副本数”不止一个字段spec.replicas 是期望值；status.replicas 是状态里的总数量；readyReplicas 是就绪数量；availableReplicas 是满足可用条件的数量。就绪与可用有关，但不总相等，例如配置了最小就绪持续时间。你的修复主要围绕期望值、就绪数与条件展开。

“就绪”是 Pod 报告的 Ready 状态，可由应用就绪探针等影响。容器进程正在运行，不代表应用已经能接收流量。因此 Running 和 Ready 也不能当成同义词。

资源、命名空间、标签：别混成一个概念

Resource
通过 Kubernetes API 管理的一类对象。Deployment、Pod、ResourceClaim 都是资源类型。“资源”在这里不只指 CPU 或内存。
Namespace
对象的逻辑分组。某些对象属于命名空间；某些属于整个集群。例如 ResourceClaim 属于命名空间，DeviceClass 是集群级对象。
Label
贴在对象 metadata 上的键值标记，例如 team=demo。用于分组与查询，不自动传给所有被引用对象。
Selector
筛选规则，例如“只查询带 team=demo 的对象”。查询结果之外的对象仍可能真实存在。
Reference
一个对象通过名称指向另一个对象，例如 Binding 的 policyName。名称相同、作用域正确，才能确定引用目标。

两种“错误”必须分开

诊断发现

某个对象配置有问题

例如一个 Claim 引用了不存在的 DeviceClass。查询成功，分析器把问题放入 Result.Error。这是工具要报告给用户的发现。

程序执行错误

工具无法完成查询

例如 API 返回权限不足。Go 函数返回 error。这不证明被引用对象不存在；应该把查询失败传给调用者。

#1743：先决定是否应该报告数量差异

  1. 没有期望值，或期望数等于就绪数 → 不报告数量差异spec.replicas 是指针，读取前要排除 nil。数量相等，仅说明没有这项差异。
  2. observedGeneration 小于 generation → 暂不报告数量差异状态仍停在旧目标版本。拿旧状态和新目标比较，容易制造误报。
  3. Available 和 Progressing 同时为 True → 暂不报告数量差异允许正常发布或扩缩容的过渡状态。它是一项抑制规则，不是对整个 Deployment 健康的完整证明。
  4. 其余数量不一致 → 保留原有诊断抑制有条件，不能把所有差异一概跳过。

#1740：发布失败要独立检查

例如旧版本仍有 3 个就绪 Pod，新版本发布却卡住。达到进展期限后，控制器可以报告 Progressing=False，reason 为 ProgressDeadlineExceeded。此时仅看“3 = 3”，会漏掉发布失败。

数量差异检查，与发布进展失败检查，
是两个独立的判断。

#1740 将 Progressing=False 检查放在数量差异条件之外。它报告这个条件的 reason 与 message；实现没有只限定某一个 reason，超时是关键测试场景。

#1743 合并提交 · deployment.go · 原始函数摘录
func shouldReportReplicaMismatch(deployment appsv1.Deployment) bool {
    if deployment.Spec.Replicas == nil || *deployment.Spec.Replicas == deployment.Status.ReadyReplicas {
        return false
    }

    if deployment.Status.ObservedGeneration < deployment.Generation {
        return false
    }

    if hasHealthyProgress(deployment.Status.Conditions) {
        return false
    }

    return true
}

bool 是 Go 的布尔类型，值写作 true / false；API 条件状态则是字符串 "True" / "False" / "Unknown"。*deployment.Spec.Replicas 取指针指向的值；|| 是“或者”，左侧成立时右侧不再求值。这个函数只回答“是否报告副本差异”，不回答“整个 Deployment 是否健康”。

展开：hasHealthyProgress 到底怎么判断？
func hasHealthyProgress(conditions []appsv1.DeploymentCondition) bool {
    progressing := false
    available := false
    for _, condition := range conditions {
        switch condition.Type {
        case appsv1.DeploymentProgressing:
            progressing = condition.Status == corev1.ConditionTrue
        case appsv1.DeploymentAvailable:
            available = condition.Status == corev1.ConditionTrue
        }
    }

    return progressing && available
}

遍历条件列表，按类型收集两个状态。&& 是“并且”。缺少任何一个条件，就不能得到两个 True。

这个方案的代价是什么？处于两个条件为 True 的过渡阶段时，数量差异被抑制。卡住的发布可能需要等 Kubernetes 报出进展失败才有明确提示；progressDeadlineSeconds 默认是 600 秒，配置可能不同，它约束缺少进展的窗口，不是整个发布的总时长。分析器没有新增自己的计时器，也没有自动回滚或修复 Deployment。

再确认一次：observedGeneration 落后只跳过数量差异，已有 Progressing=False 仍独立报告。nil 是防御性边界；真实 API 未填 spec.replicas 时通常默认成 1，不等于真实 Deployment 常常没有期望副本值。

#1765 读取与诊断策略对象，没有新增上述请求拦截流程。

三个名词，对应三件具体事情

Policy
ValidatingAdmissionPolicy：保存校验规则。两个准入策略对象都是集群级对象。
Binding
ValidatingAdmissionPolicyBinding：通过 spec.policyName 引用 Policy，并指定应用范围与校验动作。规则定义和使用规则的配置可以分开。
CEL
Common Expression Language，一种表达式语言。先理解成“对提交对象写判断条件”即可。

一条 CEL 判断，先读人话

object.spec.replicas >= 2

对正在提交的对象，读取期望副本数，判断是否至少为 2。这是表达式片段，不是完整 Policy。

类型检查告警是什么？

例如访问了不存在的字段，或对不合适的类型做操作，Kubernetes 的类型检查可能记录 warning。

warning 不等于某次请求已经被拒绝。它是规则本身需要检查的信号；你的分析器读取它。

第一条检查：把已有 warning 解释成定位信息

教学用 status 片段 · warning 文案为示意
status:
  typeChecking:
    expressionWarnings:
    - fieldRef: spec.validations[0].expression
      warning: "字段或类型使用存在问题（教学示意）"

fieldRef 是字段路径：[0] 指第一条规则。分析器把 Policy 名字、出问题的位置、原 warning 文案放进诊断。没有 TypeChecking 时跳过这项检查；有 TypeChecking 但 warning 列表为空，也不产生 Policy Result。这不是证明规则绝对正确。

为什么用了 policyChecked 和 policyExists 两张 map？

policyChecked 记住“这个名字查过了”；policyExists 记住“它是否存在”。多个 Binding 指向同一个名字时，本次分析不用重复查询。只看一个 bool=false，分不清“尚未查询”和“确认不存在”。这是本次调用中的缓存，不是跨请求、跨进程或持久化缓存。

k8sgpt 是什么？你贡献的部分在哪里？

k8sgpt 是 Kubernetes 诊断工具。它通过 API 读取集群资源，由 Go 分析器按规则生成问题列表；启用 explain 后，再使用 AI 解释这些已发现的问题。我这几项贡献在规则诊断层：新增准入策略和 ResourceClaim 分析器，并修复 Deployment 状态判定。

如果还没学懂某部分，先缩小回答到你能解释的范围，不把这段完整参考当作当前掌握的证明。

Deployment 这一条，可以怎样说完整？

原来的数量判断容易出现两个方向的问题：正常更新时期望数与就绪数暂时不同，会误报；旧版本还就绪、新版本却超时，数量可能相等，会漏报。#1743 在控制器尚未观察最新 generation、或 Available 和 Progressing 同时为 True 时，抑制副本差异诊断。#1740 则独立检查 Progressing=False，保留控制器给的 reason 和 message。fake-client 回归测试构造了正常过渡、状态滞后，以及就绪数达标但进展失败的输入。

边界是：这些条件不是完整健康证明，分析器也没自己计时或回滚。状态滞后抑制只作用于数量差异，不作用于独立失败条件。

新增分析器这一条，哪些点值得展开？

准入策略分析器读取 Kubernetes 已有的 CEL 类型检查 warning，并检查 Binding 的 policyName 目标是否存在。ResourceClaim 分析器检查设备请求的直接 DeviceClass 引用。共同的查询边界是：用户筛选要检查的对象，不应隐藏它引用的目标。前者按名字独立 Get 并在本次调用缓存；后者 List 未过滤的集群级 DeviceClass，建名字集合，再检查筛选后的 Claim。

它们是可选分析器。没有实现 CEL 引擎、DRA 调度或 GPU 分配。对 Claim 的同一缺失名字做了去重，测试包含标签和名称筛选场景；VAP 则只支持本次代码中的标签筛选。

高频追问：从定义走向取舍

为什么 observedGeneration 跟上了，发布仍不一定完成？

它说明控制器观察到了目标版本，后续创建实例、等待就绪、替换旧实例仍可能进行中。所以“状态版本已更新”和“目标已完成”是两件事。

两个条件 True，为什么不能说 Deployment 完全健康？

Available=True 只保证最低可用性；Progressing=True 也可以来自之前的进展或已完成发布。它们是该 PR 采用的数量差异抑制规则，没有检查所有故障、UpdatedReplicas 或全部发布完成条件。

如果 API 没权限读 Policy，是否输出“策略不存在”？

不能。NotFound 才进入缺失引用分支；其他查询错误向上传递。否则会把工具无法获取信息误当成配置错误。

为何 VAP 用两张 bool map，Claim 用空 struct 的 map？

VAP 要区分“是否查过”与“是否存在”，两张表显式记录两个状态。Claim 先读取完整名字集合，只需成员判断，因此用 map[string]struct{}；另一个同类型集合用于单个 Claim 内的缺失名字去重。

fake-client 测试已经通过，还需要真实集群吗？

单元测试能稳定验证给定字段、引用与查询参数下的分支。真实集群能进一步验证权限、API 支持、服务端行为与控制器实际产生的状态。它们覆盖不同范围，fake 通过不能外推生产效果。本轮学习资料没有执行上游 Go 测试或集群实验。

先认识六个 AI 应用词

LLM
大语言模型。应用把文本等输入发给它，获得生成的回答。这里用它解释诊断；能生成流利文字，不保证推断一定真实。
Prompt
本次交给模型的指令与材料。例如“请解释这条 Kubernetes 错误，用中文回答”。模板 + 实际错误文本，才能形成最终输入。
Context / 上下文
模型本次可见的信息。没有被提供的数据，不能当成它已经查看过。这里的模型上下文，与 Go 的取消上下文 Context 不同。
Provider / Model
Provider 是模型服务后端及其适配实现；Model 是实际选择的模型。同一个 provider 可以提供不同模型。
Token
模型处理文本的计量单位，不简单等于一个中文字或一个英文单词。输入与输出都占用模型容量；很多服务也按此计费。
Hallucination / 幻觉
模型输出缺乏依据或不真实的内容。例如没有读取事件，就断言某个特定权限错误是唯一根因。

Q1 · 为什么先用规则，再用模型？

源码已实现

规则负责可明确判定的事情，例如引用目标是否存在、控制器是否记录失败条件。模型负责把诊断文字变成更易读的解释与排查建议。这样可以单独测试诊断，不必为每次条件判断调用模型；不启用 explain，也能得到规则结果。

面试追问：“那 LLM 有什么不可替代的价值？”可以回答：它方便整合语言解释、可能原因和排查顺序，但仍需真实证据验证根因。领域规则不是万能的，模型也不能补出它没看到的集群事实。

Q2 · 模型实际看到了什么？

源码已实现
  1. 按一个 Result 收集 Failure.TextResult 是某个对象的诊断；Error 列表里可能有多条 Failure。GetAIResults 遍历结果，提取它们的文本。
  2. 启用匿名化时，先替换声明的敏感值使用 Failure.Sensitive 与对象身份构建映射，再对文本做替换。匿名化是选项，不是无条件执行。
  3. 选择 Prompt 模板，拼接错误文本按资源 Kind 查特定模板，没有时使用默认模板；先把错误文本拼起来，供缓存身份计算使用。
  4. 先查缓存，必要时填充 Prompt 并调用 provider缓存命中可以直接得到解释。否则把目标语言和错误文本填入模板，再调用 GetCompletion，返回解释文本。
  5. 写入 Details启用匿名化时先还原可映射的名称，再把回答放进 Result.Details。原始诊断列表与 AI 解释是不同字段。
不要把“工具能访问集群”说成“模型看过全部集群”这条主链路主要提供诊断文本，而不是把所有 YAML、日志、事件和文档完整发给模型。Failure.KubernetesDoc 的字段文档说明也不会因此自动变成检索增强输入。工具可见信息与模型本次可见信息，必须分别讲。

Q4 · Prompt 怎么设计？模型会严格听话吗？

已有模板 后半为改进设计

默认模板要求解释错误、给步骤化方案、按 Error / Solution 输出，并要求长度限制。它使用文字指令，而不是在程序中严格校验每个字段或长度。指定格式能引导回答，不能保证结果总符合要求。

如果改进，可以明确区分“观察到的事实”“可能原因”“下一步验证”，要求没有证据时说明不确定；可消费输出需要时，再采用结构化字段与校验。CLI 的 JSON 包装，不等于 LLM 本身产生了符合 schema 的 JSON。

追问：temperature 调低，是否就能解决幻觉？

不能。它影响部分模型的采样行为；更稳定的输出也可能稳定地错误。证据、任务边界、输出校验和评估都需要考虑。不要把某个参数当成真实性开关。

Q5 · 怎么减少幻觉？怎么验证解释质量？

改进设计 · 未声称项目已完整实现

先保证规则输入准确，保留资源身份、明确条件、reason 与 message；把缺失信息告诉模型，要求给可验证的下一步。生成“可能原因”时，避免改写成“已经证实的根因”。涉及命令时，还要检查资源类型、命名空间和可能影响。

测试分两层：诊断层用 fake client 检验固定输入的确定性结果；解释层用一组固定诊断案例，检查是否忠于事实、是否承认信息不足、排查步骤是否正确与有用。不要只比较文字是否完全相同，也不要把 API 返回成功当成回答正确。

可以验证的回答

“工具发现 Claim 引用的 DeviceClass 名称不存在。请先核对名字及该类别对象是否已创建。”

人写的教学例子，不是本次模型输出。

超出当前证据的回答

“这一定是某款 GPU 驱动故障，重启驱动就能修复。”

直接引用缺失不够证明驱动故障。这种回答应在解释评估中被发现。

Q6 · 为什么用缓存？哪些变化应该让缓存失效？

固定版本现状

重复诊断可以复用解释，减少延迟与模型调用。该基线用 provider 名、语言和拼接后的错误文本生成缓存 key；代码留有 model 等配置维度的 TODO。最终 Prompt 模板也没有直接进入这次 key 的参数。

代码推导 在同一缓存范围内，只切换模型或模板、其他输入相同，缓存身份仍可能相同。这是源码推导的边界；本轮没有真实切换模型复现，也不据此宣称发生过生产故障。

改进设计 先定义“什么情况下两次解释请求等价”。可考虑模型、最终 Prompt / 模板版本、语言，以及影响输出的服务配置。敏感凭据不应作为可见 key 字段；缓存中的文本是 base64 编码，也不等于加密。

追问：怎么测试缓存，不用真的调用模型？

用能记录调用次数、返回固定文本的 fake provider。相同输入应复用；模型或模板变化按设计应重新调用。分别检查返回哪份答案、provider 被调用几次，避免只断言内部 hash 长什么样。

Q7 · 模型超时或限流，会怎样？你会如何改进？

固定版本现状

规则诊断先完成，但 CLI 启用 explain 后，GetAIResults 返回错误会退出，正常打印结果的步骤不再执行。因此“代码先诊断”并不自动保证“AI 失败仍把基础结果展示给用户”。该循环遇到第一个解释错误就返回。

改进设计 可以保留基础诊断，把解释状态单独标为失败，向用户说明部分解释不可用。再区分瞬时限流、鉴权错误、配额问题、用户取消；只对适合重试的错误做有限重试，并受总期限约束。不要对所有错误无限重试，也不要默认一个 429 只有一种原因。

追问：并发更多模型请求，是否一定更快？

不一定。固定基线的 AI 结果循环是串行；分析器并发参数不能直接等同模型并发。若要改进，还要核对客户端与缓存能否并发使用、限制总并发、处理限流、保留结果归属和取消传播。一次请求更快与整体服务更稳，可能有取舍。

Q11 · Tool calling 到底是什么？

工具
程序提供的一项能力，例如读取某个 Pod 的事件。有名字、用途、输入参数和返回结果。
模型提出调用

程序执行
应用验证参数、权限和调用条件后执行，再把工具结果提供给模型。
循环与停止
模型根据新结果决定下一步或给出答案；运行时约束步数、时间、成本、重复调用和失败行为。
“模型给了 kubectl 命令”不等于“模型调用了工具”文本建议与真实执行是两件事。固定版本的普通模型适配器返回文本；某些模板请求命令建议，不能据此宣称有自动修复闭环。

Q12 · MCP 是什么？支持 MCP，就自动有 Agent 吗？

模型是否自主选工具、如何保留历史、什么时候停止，仍需要客户端或其他运行时组织。MCP 本身不提供所有这些决策逻辑。固定版本还注册了资源 list / get、事件与日志读取等工具；config 和 add / remove filters 可修改本地配置。所查集群操作为读取，不包含 kubectl apply / delete 式的资源修改；“所有工具都只读”与“已有自动修改集群”这两种说法都不准确。

固定版本源码观察

该版本 interactive 路径把初次分析输出与当前问题组成新的 Prompt。所查文件没有持续追加之前每轮问答的历史。所以“界面能反复提问”和“模型每轮都能看见全部聊天历史”不是同一件事。

改进设计 真正维护多轮上下文时，要明确会话归属、历史顺序、资源范围、最大长度，以及新证据是否替代旧证据。可以先做有界会话状态；不必一开始建立长期记忆系统。

Q14 · 这里有没有 RAG？什么时候值得加？

RAG
Retrieval-Augmented Generation，检索增强生成。先从外部资料取相关内容，再把资料作为模型生成的依据。
常见资料
匹配版本的 Kubernetes 文档、团队排障手册、驱动说明等。检索可能用关键词，也可能用向量相似度，不等于必须有向量数据库。

源码观察 本册所查主解释链没看到文档检索、选择片段、再注入 Prompt 的完整路径。--with-doc 可以从 API Discovery 读取 OpenAPI Schema，为字段说明提供资料；但 GetAIResults 读取的是 Failure.Text，不会自动把独立的 KubernetesDoc 字段拼进去。存在 API 文档补充，也不等于已经建立面向知识库的检索增强链。

改进设计 当模型缺少特定版本、内部流程或驱动资料时，可以检索相应文档，保留来源与版本，并核对回答是否被资料支持。如果已有诊断足够，不一定每次都需要检索；多一层检索，也多一层错误、延迟与权限处理。

Q15 · 如果改成排障 Agent，你先做什么？

设计题 · 不是本人的既有贡献
  1. 先定义一个小任务与完成条件例如解释一个 Deployment 的发布异常；输出已证实事实、未证实假设与下一步。
  2. 提供有结构的证据查询工具例如查询选定资源状态与相关事件。限制资源范围，保留来源和观察时刻。
  3. 让每次调用都回到证据模型选查询 → 程序执行 → 返回结果 → 模型再判断。没有证据时允许停止并说明未知。
  4. 限制循环成本与错误传播步数、总时间、并发与取消都要有边界。工具失败不是“资源不存在”，也不是允许模型凭空补答案。
  5. 另行设计写入操作如果需要修改集群，先形成可审阅方案，再按实际权限与用户授权执行，并验证结果。不将任意模型命令直接交给 shell。

这些是面试里的设计取舍。现有 MCP 工具集必须按源码逐项核对；该方案不意味着原项目已经实现这个循环，或所有现有写入工具都具有同样的审阅与验证机制。

Q16 · 怎么评估一个排障 Agent，而不是只听它说得好？

设计题
层测试或评估的问题
诊断事实正常、异常和过渡状态是否正确？引用筛选是否误报？用确定性用例验证。
模型解释是否忠于已知事实、区分猜测与结论、引用可用来源？用固定案例加人工判断或明确评分标准。
工具调用参数、权限、命名空间是否正确？是否越界、重复调用或把查询失败当成缺失？
任务完成是否找出可验证的原因或合理地停止？如果执行修改，是否实际验证目标状态？
应用成本延迟、调用数、Token、失败与取消路径是否可接受？和简单规则流程相比是否有实际收益？

fake 模型和假客户端可以验证编排契约；真实模型与固定任务集帮助评价回答和决策质量。没有做过这些实验，就不能在简历里写通过率或成本改善数字。
